    2 · Data received

    Ticks are what each deployment's capture wrote to ticks.csv. Bars are the 1-minute bars it built from them. Deployments on the same contract receive the same tape, so differences in their counts come only from different start times.

    Feed quality

    A bar is only built for a minute with at least one trade, so a session can have fewer than 300 (day) or 840 (night) bars with nothing lost. Lost minutes are minutes that do have trades in ticks.csv but no bar; any number above 0 is a real gap. A feed check runs when the stream goes quiet and asks the venue whether anything was missed. A quiet verdict means nothing was. The delay figures include any clock offset between this PC and the exchange.

    3 · Decisions

    Every stride bars, each deployment forecasts the next horizon bars. It emits BUY or SELL only if four gates pass in order: the predicted return crosses the band, the directional probability ≥ min_prob, the trend filter agrees, and path momentum agrees. Otherwise it emits HOLD.

    Decision funnel

    The band and min_prob stages are rebuilt from each forecast's predicted_return and prob_up. The trend and path stage is what is left once emitted signals are counted.

    4 · Position

    Position is checked twice: by each deployment (the position on every bar) and by the owner, which publishes the account position to each deployment (events_<slug>.jsonl).

    Position over time

    5 · Stability

    A Shioaji token expires 24 h after login, so every process logs in again on a schedule before each session opens. A deployment confirms each re-login a few minutes later.

    Logins per process, by session
    Each cell is one successful login (“stored new token” in shioaji.log, in local time), grouped by the session open it came before. Failed attempts come from each deployment's session.jsonl.
